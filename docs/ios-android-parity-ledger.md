# iOS–Android parity ledger

This ledger freezes Android commit `2f56aa4` as the behavioral baseline for the iOS parity release. Executable Android code and tests remain authoritative when this document and historical PRDs disagree.

The route inventory comes from `AwradDestination.kt` and contains 24 destinations. Each Android destination appears exactly once below and is owned by exactly one implementation slice. The owning slice also owns every state listed in that row and every applicable cross-cutting state. Slice 10 reviews those surfaces; it does not become a second implementation owner.

Parity means matching information hierarchy, state transitions, actions, and persisted outcomes with an iOS-native SwiftUI presentation. It does not mean copying Material components pixel for pixel.

## Closure vocabulary

- **Implemented in tree**: the destination is wired to the cited source. This does not by itself claim that runtime acceptance passed.
- **Automated evidence**: a focused test or fixture exists at the cited path. Test results belong in the implementation handoff, not this ledger.
- **Runtime open**: the source exists, but the applicable visual, lifecycle, permission, or integration evidence still has to be recorded in [`ios-parity-debugger-review.md`](ios-parity-debugger-review.md).
- **Physical device**: the behavior depends on hardware, signing, extensions, or a system service that a simulator cannot prove. It remains an explicit release check rather than being treated as an implementation gap.
- **Intentional iOS equivalent**: the Android action is represented through the named native iOS surface.

All identifier-backed routes must show a recoverable unavailable state for stale input. They must never crash or silently substitute an unrelated record.

## Cross-cutting state contract

For each route row, the named slice owns every applicable state below. A state that does not apply must be marked `N/A` with a reason in the runtime review; it must not be silently skipped.

- **Data:** initial loading, ready, empty, referenced-record missing, local read/write failure, and relaunch restoration.
- **Network:** online success, offline local usability, timeout/server failure, retry, and no indefinite loading indicator.
- **Permissions:** not determined, granted, denied, restricted/unavailable, and return from the iOS Settings app.
- **Mutation:** idle, validation error, in flight with duplicate submission prevented, committed success, failure with entered data preserved, and cancellation.
- **Navigation:** direct entry, back/cancel, successful return destination, stale deep link, and state restoration after termination.
- **Presentation:** light/dark, English, Arabic RTL, Malayalam, large Dynamic Type, VoiceOver, Reduce Motion, and Reduce Transparency. iOS 26+ uses system Liquid Glass and limited interactive custom glass; iOS 18–25 uses the documented material/opaque fallback.

## Intentional platform differences and environment limits

- Android exact alarms and battery-optimization management map to local-notification authorization/status, reconciliation, and the iOS system Settings deep link.
- Material navigation and controls map to native SwiftUI navigation stacks, sheets, toolbars, tabs, and gestures while retaining hierarchy and action placement.
- Location accuracy, real notification delivery, audio-route interruptions, interactive widget/App Intent behavior, Live Activity lifecycle, and signed App Group concurrency require a physical device for final acceptance.
- Simulator review can prove request construction, scheduling reconciliation, UI states, route restoration, locale/layout direction, and most accessibility presentation; it cannot be recorded as proof of the physical-device items above.
- Progress synchronization and new Community/social features remain outside this parity release.
- Devotional wording and translations require separate human scholarly/language review; structural localization parity is not that review.

## Closing a ledger row

A row closes only when all of the following are true:

1. The Android behavior at `2f56aa4` and every intentional iOS equivalent are represented in source plus focused automated evidence or an explicit environment-bound note.
2. All applicable data, network, permission, mutation, navigation, and presentation states are recorded in [`ios-parity-debugger-review.md`](ios-parity-debugger-review.md); skipped cells say why.
3. User-facing copy exists in English, Arabic, and Malayalam resources, including validation and recovery messages.
4. iOS 26 Liquid Glass and iOS 18 fallback are reviewed in light/dark mode, Arabic RTL, large Dynamic Type, VoiceOver, Reduce Motion, and Reduce Transparency.
5. `./check-mobile-model-parity`, the focused and broad iOS tests chosen in [`TESTING.md`](../TESTING.md), localization key/parse checks, and `git diff --check` have recorded results.
6. Physical-device requirements are either passed on the target hardware or left explicitly open for release sign-off; simulator evidence must not be substituted.
