# awrad-ios-next — architecture

The Awrad iOS app, rebuilt to replace `awrad-ios/` (root ADR-2026-10-14).
- **Stack:** SwiftUI, SwiftData and Observation on iOS 18, built with Xcode 26.2 / Swift 6.2.
- **Status:** scaffold plus the slice 1 and 4a goal rules, the slice 1b Hijri calendar, the slice 2a and 2b accounts, the slice 3a dhikr catalog and Library, the slice 3b custom dhikrs, tags, local profiles and change queue, the slice 3c private audio uploads, and the slice 3d practice settings. A placeholder onboarding screen and home screen prove the wiring; features arrive in slices (`../docs/rebuild-plan.md`).

## Modules

All code lives in one local Swift package, `AwradKit`. The Xcode project holds only a thin app target (ADR 0003).

```mermaid
flowchart TD
  app["AwradNext app target<br/>composition root, root routing"]
  feat["Feature* targets<br/>Route + Screen + @Observable model"]
  domain["AwradDomain<br/>Foundation only: types, rules, ports"]
  data["AwradData<br/>SwiftData, UserDefaults, Keychain, API client"]
  ds["AwradDesignSystem<br/>colours, fonts, components"]
  testing["AwradTesting<br/>one fake per port"]
  app --> feat & data & ds & domain
  feat --> domain & ds
  data --> domain
  testing --> domain
```

| Target | May depend on | Isolation |
|---|---|---|
| `AwradDomain` | nothing (Foundation) | nonisolated |
| `AwradData` | `AwradDomain`, and `Adhan` (adhan-swift, ADR 0006) | nonisolated (actors for state) |
| `AwradDesignSystem` | nothing | `@MainActor` by default |
| `Feature*` | `AwradDomain`, `AwradDesignSystem` | `@MainActor` by default |
| `AwradTesting` | `AwradDomain` | nonisolated |
| Test targets | whatever they test, plus `AwradTesting` | as tested |

**Enforcement:** the compiler blocks imports a target doesn't declare, and `scripts/check-module-rules.py` blocks declarations outside this table (ADR 0001).

**Platforms:** the package targets **iOS 18 and macOS 15**, so `swift test` runs domain, data and model tests on the Mac in milliseconds. Only app-level checks need a simulator.

## IDs

Every ID is an `AwradID`, and every ID the app generates is a UUIDv7 ([`contracts/identity/v1`](../contracts/identity/v1/README.md), root ADR-2026-10-28): entity IDs, the installation ID and `Idempotency-Key`s.

- **Generator** (`AwradDomain/UUIDv7.swift`): `UUIDv7.uuid(unixMilliseconds:random:)` is the pure layout from a time and 10 random bytes, run against `uuid_v7_layout.json`. `UUIDv7.generate(now:using:)` takes the clock and a `RandomNumberGenerator`; production (`AwradID.random()`) uses `Date.init` and `SystemRandomNumberGenerator`, which is cryptographically secure on Apple platforms. A clock before 1970 gives time zero.
- **Validation:** `AwradID.init?(_:)` accepts only the wire form (`uuid_format.json`): lowercase, hyphenated, any version (built-in dhikrs keep their fixed UUIDv4s), never the nil or max UUID, nothing trimmed or case-folded.
- **Never by timestamp:** nothing orders, expires or authorizes by an ID's time; the device clock can be wrong.
- **Check:** `scripts/check-uuid-generation.py` (in `scripts/validate`, after its `--self-test`) rejects `UUID()`, `UUID.init()` and `NSUUID()` in `AwradKit/Sources` and `AwradNext`, since Foundation only makes v4. Tests may use them for throwaway names.
- **Runner:** `IdentityFixtures` runs `identity/v1/fixtures/`; `UUIDv7GeneratorTests` checks that consecutive IDs are valid v7 that sort by time.

## Goal model and rules (slices 1 and 4a)

`AwradDomain` models [`contracts/goal-model/v1`](../contracts/goal-model/v1/README.md) as Sendable value types:
- `Goal.swift` and `GoalSettings+Parts.swift`: `Goal` (what a rule evaluates on one day: a version's `GoalSettings` plus pauses and excused days), `Schedule`, `ActivePeriod`, `PausedRange`, `CountPolicy` with its `StreakThreshold`, `GoalSession` with its `SessionKind` (the ID is derived from the kind), `Requirement`, `CompletionPolicy`, `MakeUp` and `CountEntry`.
- `GoalDocument.swift`: `GoalTimeline` (dated `GoalVersion`s, pauses, excused days, `GoalEnding`), `GoalDocument` (adds the dhikr ID, `DhikrSnapshot`, name and `GoalCounts`), `GoalOrder` and `CountLogEntry`. A lone `Goal` stands for a one-version timeline (`GoalTimeline(goal)`).
- **Days** are `CalendarDay` (year, month, day), not `Date` or `DateComponents`. Day arithmetic is plain ordinal arithmetic in the proleptic Gregorian calendar, never `Calendar.current`. `CalendarDay` is `Strideable`, so a window is a walkable `ClosedRange<CalendarDay>`.
- **Only valid goals exist.** `GoalSettings` and `GoalTimeline` have read-only properties and initializers that `throw(GoalValidationError)`, whose `codes` are the contract's error codes in alphabetical order (`Goal+Validity.swift`, run against `goal_validity.json`). Every caller (fixture decoding, tests, later sync and import) goes through them, so the rules never handle a missing target.
- **One file per rule**, all pure. On a single day: `EffectivePracticeDay.resolve`, `Goal.isDue(on:)`, `Goal.standing(…)`, `Goal.daysPerPeriodStanding(…)` and `Goal.isCompleted(…)`. Across days, on a timeline, each day judged by its version (`GoalTimeline+Versions`): `dueDayStatuses` (make-up), `streak`, `consistency`, `dailyPace`, `todayRing`, `excuseRefusal`/`unexcuseRefusal`, `listSection`/`finish`; plus `GoalList` (placement and order), `GoalOrder.merge` and `CountAttribution`. They share `GoalEvaluation.swift`: the count ledger, the units a day is judged on, the only place that decides whether a window meets its numbers, and `TimelineEvaluator`.
- **Fixture runner:** `AwradTesting/FixtureLoader.swift` reads `contracts/<model>/v<N>/fixtures/<rule>.json` from the repository (found by walking up from `#filePath`) and fails on a missing file, zero cases or a case that won't decode. `GoalModelFixtures` decodes each rule's `given` into domain values. `AwradDomainTests/GoalModelFixtureTests` and `GoalTimelineFixtureTests` run every case as a parameterized test named by case ID.

- **Sync (contracts/sync/v1, slice 4):** `SyncEntityType.goal` and `.goalOrder`, `SyncDocument.goal(GoalDocument)` and `.goalOrder(GoalOrder)` with their wire codec (`Sync/GoalDocument+JSON.swift`; schedule sets are written Monday first, the rest ascending). `GoalDocumentValidation` checks a goal document's structure, then the goal rules as field errors (`goal_document_validity.json`); `GoalDocument(json:)` throws its errors. A `goal_field_immutable` rejection restores the server's copy like other rejections, and a goal conflict whose server copy is deleted removes the goal with the notice. A goal's command references its custom dhikr and a goal order's its goals (`OutboxCommand.references`). Deleting a custom dhikr ends its goals locally (`SyncRules.save(_:queue:today:in:)`), and when its create was never sent drops their unsent commands. A goal `conflict` takes the server's copy with the `goal_edit_not_applied` notice unless nothing was lost; a goal order merges against its base like the practice policy (`SyncEntityType.mergesAgainstBase`). `queueAll` leaves the goal order out; the profile merge adds goals and appends them to the account's order. Each profile stores them as `GoalDocumentRecord` and `GoalOrderRecord` (with its base). Not yet built (4b): the goal order decided after the first complete pull, and the screens that save goals.

The fixtures are the spec. The goal screens and their store are slice 4b; the old `GoalRecord` in the shared store is still a placeholder subset.

## Hijri calendar (slice 1b)

Hijri dates come from the shared Umm al-Qura table of [`contracts/hijri-calendar/v1`](../contracts/hijri-calendar/v1/README.md) (root ADR-2026-10-26), never from Foundation's `.islamicUmmAlQura`.
- **Bundling:** `scripts/generate-hijri-table.py` compiles `umm-al-qura.json` into `AwradDomain/UmmAlQuraTable.swift` (month starts as days since 1970-01-01), so the app works offline and nothing reads `contracts/` at runtime. Never edit the generated file; rerun the script.
- **Freshness check:** `scripts/validate` runs the script with `--check`, which fails when the Swift file differs from what the contract generates. `UmmAlQuraTableTests` also checks every decoded month start against the JSON.
- **Corrections:** `HijriCorrections` is a valid set of month-start corrections. Its initializer `throws(HijriCorrectionsValidationError)` with the contract's codes, so an invalid set can't exist. Its `calendar` (a `HijriCalendar`) is the table with them applied: `date(of:)` and `month(containing:)` return `nil` outside the table.
- **Rules:** the schedule kinds `hijriMonthDays` and `yearly` (Gregorian or Hijri `YearlyRange`s) and the period `hijriMonth`. Every rule that reads Hijri dates takes `hijriCorrections:` (default `.none`).
- **Runner:** `HijriCalendarFixtures` runs `hijri-calendar/v1/fixtures/`. `FixtureRunnerTests` fails if either fixture directory has a file no rule runs.

## Accounts (slices 2a and 2b)

An account is optional: everything offline works without one, and signing in or out, or deleting the account, never touches local practice data (root ADR-2026-10-26, ADR-2026-07-12).

- **Input rules** (`AwradDomain/AccountInput.swift`): `AccountInput.email`, `AccountInput.emailCode` and `PasswordPolicy` implement [`contracts/account-model/v1`](../contracts/account-model/v1/README.md). Lengths are Unicode scalars (after NFC for passwords), never `String.count`; whitespace is the contract's explicit set. `AccountModelFixtures` runs the fixtures, and `FixtureRunnerTests` covers the directory.
- **Port:** `AccountService` (`AwradDomain`), with `Account`, `AccountSession` and `AccountError`. The fake is `FakeAccountService`.
- **API client** (`AwradData/Network/`, ADR 0004):
  - `APIOperation` lists every operation the app calls, by `operationId`.
  - `APIClient` attaches a bearer token only to operations that take one, an `Idempotency-Key` (lowercase UUIDv7) to every `POST`, and `Accept-Language` (the app language) where the spec declares it. An operation's `path` is the spec's template; `pathParameters` fill its `{name}`s, and `queryParameters` lists the query names it may send.
  - Nullable response fields (`AccountSession.name`, `next_cursor`) are encoded as `null`, never left out, so a round trip is exact. Unknown `kind` or `platform` values become `.other`.
  - Wire types are hand-written `Codable` structs (root ADR-2026-10-16). Problems are RFC 9457 and map to `AccountError` by `code` only.
  - Transport: an ephemeral `URLSession` without cookies or cache.
  - `OpenAPIContractTests` checks every used operation against `contracts/api/openapi.bundled.json` and round-trips every example.
- **Session** (`AwradData/Account/AuthSession.swift`, an actor, ADR 0005):

  | Concern | Behaviour |
  |---|---|
  | Storage | Installation ID and `device_session` (account, refresh token, pending refresh key) in the Keychain, `AfterFirstUnlockThisDeviceOnly`. The access token only in memory |
  | Reinstall | A `UserDefaults` marker; without it, Keychain leftovers are removed on first use |
  | Refresh | Single-flight. Sends an `Idempotency-Key` saved before sending and reused when retrying the same refresh. Drops credentials only on `refresh_token_invalid` or `refresh_reuse_detected` |
  | Authenticated calls | Refresh when there's no valid access token (60 s margin), and once more after `unauthenticated`, reusing the request's `Idempotency-Key`. A second `unauthenticated` means the session ended elsewhere: credentials cleared, `.signedOut` |
  | Settings (`AuthSession+Settings.swift`) | `list_account_sessions` follows `next_cursor` (100 per page, 10 pages at most). `delete_account` clears the credentials on `204` without calling sign-out: the server ended every session. `confirm_email_change` stores the account's new email |
  | Sign-in | `create_device_session` with the installation ID and `DeviceName.current()` (marketing name of the model, never "Apple device") |
  | Sign-out | `sign_out_device_session` with the refresh token, then credentials cleared, even offline. The installation ID stays |

- **UI** (`FeatureAccount`): one `AccountRoute` and `AccountModel` drive a `NavigationStack`, tinted `AwradColors.accent` so the back button and toolbar items are the app's green and stay readable in dark mode.
  - **Signed out:** sign in, then pushed steps for create account, verify email (resend with a 60 s cooldown, or `Retry-After`), forgot password and reset password. Verifying or resetting signs in with the password just typed.
  - **Signed in** (slice 2b): the overview shows the email, rows for Devices, Change password, Change email and Delete account, and sign out.
    - *Devices:* this device first and marked, then the others with their platform and relative last use; "Web browser" (or "Unknown device") when `name` is `null`. Each other one has Sign out, behind a confirmation; "Sign out of all other devices" too. This device signs out from the overview.
    - *Change password:* current and new password (length rule checked first). Back to the overview with a notice that other devices were signed out.
    - *Change email:* current password and new email (shape checked, and must differ), then the code sent to the new address with the resend cooldown, then the overview with the new email.
    - *Delete account:* says the account and its server data go now with no undo, and the data on this device stays; current password, then a destructive confirmation. Ends at sign in with a notice, email not prefilled.
  - **Session ended:** when any signed-in call returns `.signedOut` (revoked elsewhere, or a rejected refresh), the adapter has already cleared the credentials and the model shows sign in with "you've been signed out", the email prefilled. Local data is untouched.
  - **Local actions** (typing, navigation, asking to confirm) go through the synchronous `apply(_:)`; only server work runs in a task.
  - **Text:** numbers are format arguments, never digits inside a translation, so a screen uses the locale's digits throughout (counts, the countdown, `Date.RelativeFormatStyle` for last use). An email or device name never sits inside a sentence: it's its own `Text(verbatim:)` run (no Markdown, no link detection), wrapped in FSI…PDI (`Strings.isolated`), also where a device name fills a confirmation title.

  `AccountModel.Feedback` gives each handled error code its own localized text:

  | Code | Shown as |
  |---|---|
  | `validation_failed` | its field code: `email_invalid`, `email_unchanged`, `password_too_short`, `password_too_long`, `password_too_common`, `current_password_incorrect` |
  | `invalid_credentials`, `verification_code_invalid`, `reset_code_invalid`, `email_change_code_invalid`, `email_taken` | their own text |
  | `not_found` (revoking a device) | "already signed out", and it leaves the list |
  | `email_verification_required` | goes to the code screen, with a notice |
  | `rate_limited` | wait text, with `Retry-After` seconds when present |
  | `refresh_token_invalid`, `refresh_reuse_detected`, `unauthenticated` after a fresh token | signed out, with its message |
  | no response | can't reach Awrad |
  | anything else (`malformed_request`, `idempotency_key_reused`, `csrf_token_invalid`, unknown codes, `5xx`) | something went wrong |

- **Entry point:** the home screen's Account button opens `AccountRoute` in a sheet (`RootView`).
- **Base URL** (`AppComposition`'s `APIEnvironment`): Debug uses `http://localhost:4000`. `Config/Debug-Info.plist` (Debug only) allows plain HTTP to `localhost`. Release has no server yet, so it points at a `.invalid` host.

## Dhikr catalog and Library (slice 3a)

The built-in dhikrs and collections of [`contracts/dhikr-catalog/v1`](../contracts/dhikr-catalog/v1/README.md), read-only and in memory (no SwiftData; custom dhikrs come in 3b).

- **Bundling:** `AwradDomain/Resources/dhikr-catalog.json` is a byte-identical copy of `catalog.json`. `scripts/check-dhikr-catalog.py` (in `scripts/validate`) fails on drift; `--fix` copies the contract's file. `DhikrCatalogTests` also compares the two. Nothing reads `contracts/` at run time.
- **Types** (`AwradDomain/Dhikr.swift`, `DhikrCatalog.swift`): `Dhikr` (`AwradID` id, key, `DhikrKind`, Arabic, `LocalizedText` title, transliteration and translation, aliases by `CatalogLanguage`, tag keys, `DhikrAudio?`, `[Reference]`, `[Virtue]`), `Reference` (an enum: `quran(id:surah:ayahs:)` from `ayah_start`/`ayah_end` since content revision 4, `hadith`, `book`, `shaykh`, `other`), `Virtue`, `DhikrCollection`, `CatalogTag`, `DhikrAudio`. `DhikrCatalog.bundled()` decodes the copy; the app decodes it once in `AppComposition`.
- **Decoding** (`DhikrCatalog+Decoding.swift`): every object rejects keys the schema doesn't list, and only a consistent catalog exists: `DhikrCatalog`'s initializer `throws(DhikrCatalogError)` on another `version`, a repeated key, or a collection, tag or virtue reference that resolves to nothing.
- **Display** (`Dhikr+Display.swift`): `dhikr.display(in:)` gives the title, transliteration and translation in the app language (`CatalogLanguage(languageCode:)` from `Bundle.main.preferredLocalizations`), each falling back to English; Arabic has no transliteration.
- **Search** (`DhikrSearch.swift`): `DhikrSearchNormalization.normalize` is the fixture's nine steps, on Unicode scalars (combining marks by `generalCategory`, Malayalam signs kept). `DhikrSearchIndex(dhikrs:language:)` precomputes each dhikr's compact names and fields as UTF-8 and matches bytes, so a query can end inside a Malayalam grapheme. `DhikrCatalogFixtures` runs both fixture files (`dhikr_search` over the bundled catalog); `FixtureRunnerTests` covers the directory.
- **Audio:** the `DhikrAudioPlayer` port (`@MainActor`; `play(url)`, `pause()`, `stop()`, and `onStatusChange` with `AudioPlaybackStatus`, whose `PlaybackPosition` carries the elapsed time and, once the stream knows it, the length). `AVDhikrAudioPlayer` (`AwradData/Audio`) streams `audio.url` with `AVPlayer`, sets the session to `.playback` (`.spokenAudio`) when playing and releases it on `stop()`, and reports the time every 0.25 s. `AppComposition.makeAudioPlayer` makes one per dhikr screen; the fake is `FakeDhikrAudioPlayer`. Built-in recordings stream; a custom dhikr's uploaded recording is downloaded once and played from the file (slice 3c, below).
- **UI** (`FeatureLibrary`):
  - **Shell** (`AwradNext/AppShell.swift`): Home and Library under `awradBottomBar`, switching with `awradTabSwitch`. The bar shows only on the two roots: a pushed collection or dhikr hides it (`isPresented:`). The shell owns `LibraryModel`, so Home's tiles open a collection in the Library tab and "View all" opens the Library's first screen.
  - **Home** keeps the placeholder content and adds `FeaturedCollections`: the `sectionTitle` heading with a "View all" text button, then a horizontal row of `AwradCollectionTile`s ("100 dhikrs" from the catalog's plural variants).
  - **Library** (`LibraryRoute` over `LibraryModel`): the native large title, a search field (the `search` icon in an `awradField`, a clear button), then Collections (tiles) and All dhikrs (rows). While the query isn't blank, only the results show, or the empty state. Typing goes through the synchronous `apply(_:)`.
  - **Dhikr row:** a `tile` card button with the title in `rowTitle`, one right-to-left line of the Arabic in `quranLine` (truncated, on the right in every language, exactly the style's line height so the row hugs it), and a `chevron`.
  - **Collection:** a native push with the collection's title, then its rows in order.
  - **Dhikr detail** (`DhikrDetailRoute` over `DhikrDetailModel`): a card with the Arabic, centred and right to left (`quran`: one ayah per line in `quran` and the reference label, "Qur'an 112:1–4", in `caption`; `name_of_allah`: the name in `nameOfAllah` over its meaning in `title`; other kinds: the whole text in `quran`), and at its bottom the audio player bar when there's audio (`DhikrAudioBar`: the play/pause `AwradRoundButton`, a progress indicator while loading, a `ringStroke` progress line, and "0:14 / 0:26" in `caption`; before the first play the length is the document's `duration_ms` when it has one, otherwise the elapsed time shows alone until the length is known). Then the transliteration and translation (every kind but `name_of_allah`), the tags as chips, and the virtues in `tile` cards with their reference labels (`ReferenceLabel`: hadith collection, number and grade; book title, author, volume:page; shaykh name; other text and link). Leaving the screen stops the audio, and the app going to the background (`scenePhase`) pauses it. The player is made on the first play.
  - **Screenshots** (debug builds): `-AwradTab library`, `-AwradLibrarySearch <query>`, `-AwradLibraryCollection <key>` and `-AwradLibraryDhikr <key>` open the Library in that state; `-awrad.onboarded YES` skips onboarding.

## Custom dhikrs, tags and the change queue (slice 3b)

The phone side of [`contracts/sync/v1`](../contracts/sync/v1/README.md) (root ADR-2026-10-28 "The change queue"). Everything works signed out and offline; sync layers on top (ADR-2026-10-28 "complete without an account").

- **Domain** (`AwradDomain/Sync/`), pure and fixture-driven:
  - `AwradJSON` keeps documents exactly (integers stay integers); `SyncDocument` is `customDhikr(CustomDhikrDocument)`, `userTag(UserTagDocument)` or `dhikrPersonal(DhikrPersonalDocument)`, with `init(type:json:)` and `json`. `CustomDhikrDocument` keeps its references as catalog-shaped JSON (`typedReferences` reads them, a backwards Qur'an range in order) and `dhikr(id:)` gives the catalog `Dhikr` the Library shows.
  - `TagName.normalize`: trim and collapse Unicode `White_Space` on scalars, NFC; the normalized name is full, locale-free case folding (`folding(.caseInsensitive, locale: nil)`, so `ß` → `ss`, `İ` → `i̇`), then NFC; limits on graphemes then UTF-8 bytes.
  - `CustomDhikrValidation.errors(in:)`: the schema's rules on raw JSON, sorted `{field, code}` JSON Pointers; "blank" is ECMAScript `\S`, lengths are code points.
  - `SyncRules` (`save`, `enqueue`, `queueAll`, `merge`, `apply(page)`, `apply(receipts)`, `resolve`) run over the `SyncLocalState` protocol, so the fixtures (`InMemorySyncState`) and the SwiftData store share one implementation. A rule touches only the entities it names: **each edit records its own command; nothing diffs the store.**
    - **Replacing a never-sent command** keeps its `command_id`, `base_version` and position, unless its document references a tag or its own custom dhikr whose never-sent put is later in the queue (`OutboxCommand.references`): then it moves to just after the last such put (`SyncLocalState.moveCommand`), so it never reaches the server before what it names.
    - **Deleting a tag** queues only the tag delete and takes the tag out of personal records and never-sent personal commands in place; the server cascades it.
    - **Pages:** a delete cleans up as a `gone` receipt does, even with queued commands or an open conflict (unsent commands dropped, conflict closed). **Receipts:** `applied` carries `cascaded` (`SyncCascade`) for a tag or custom dhikr delete, and each entry moves the known version of a record the phone has (a deleted one is removed).
    - **`merge(_:into:)`** is "Add to my account" into an account's existing profile: same-name tags fold onto the account's, a shared personal record gets the union of tags (the account's first, capped at 20), and every merged entity is queued as a put.
  - `CustomDhikrValidation` adds the rule the schema can't express: a Qur'an reference's `ayah_end` below its `ayah_start` is `range` on `/references/N/ayah_end`.
  - `ProfileSwitch.prompt(for:in:)` and `apply(_:choice:to:newProfileID:)` are the `profile_switch` state machine over `ProfileRegistry`. Signing in from an anonymous profile with data always asks; for an account that already has a profile, Add returns a `ProfileMerge` and Erase discards the anonymous data (an empty anonymous profile stays). Removing the active profile activates the anonymous one, or a fresh one. Keep on a deleted account marks the profile `accountDeleted` (`discardUnsent`): it never queues (`LocalProfile.queuesEdits`) or syncs again.
  - Ports: `PersonalLibrary` (content and its updates, custom dhikr save/delete with an `AudioChange`, tags, `setTags`, conflicts, notices, staged audio) and `LocalProfiles` (registry, `SyncStatus`, prompts, `handle(_:choice:)`, `syncNow`). Fakes: `FakePersonalLibrary`, `FakeLocalProfiles`.
- **Runner:** `SyncFixtures` loads the five phone files with their keys as written (`FixtureLoader.load(…, convertingSnakeCase: false)`); `SyncFixtureTests` runs every case, a merge case's `merge_data` through `SyncRules.merge`; `SyncFixtureCoverageTests` fails on a file that is neither run nor server-only (`sync_receipts`, `sync_changes_feed`). `SyncPersistenceTests` runs `outbox_enqueue`, `apply_changes` and the `profile_switch` merge again on SwiftData.
- **Local profiles** (`AwradData/Profiles/`): `LocalProfileStore` (an actor) is the adapter for both ports.
  - **Files** (`ProfileFiles`, under Application Support/Profiles): `registry.json` (profiles with local ID, account, email, feed `after`, has data, has unsent, account deleted, last used; the active profile; the signed-in account), and per profile `<id>/profile.store` (its SwiftData store, recreated when incompatible per ADR 0002) and `<id>/Audio/` (recordings, plus `Staged/` for one picked but not yet saved). Removing a profile deletes its directory. A path handed to the file system is `path(percentEncoded: false)`, never `path()`, which encodes the space in `Application Support` (`scripts/check-file-paths.py`, in `scripts/validate` after its `--self-test`); the data tests' profile root has a space and non-ASCII characters (`TestDirectory`) to catch it.
  - **Switching** swaps the `ProfileDatabase` (a `@ModelActor` over the profile's container); `updates()` of both ports republish, so the screens follow. A `ProfileMerge` reads the anonymous database's documents, merges them into the account's in one transaction and moves its recordings before the anonymous profile is erased; Keep on a deleted account empties that profile's outbox. `start()` reconciles the registry with `AuthSession` at launch (a session that ended while closed signs out; a sign-in whose first-sign-in question never got an answer asks again).
  - **Records** (`ProfileRecords.swift`): `CustomDhikrRecord` (document JSON), `UserTagRecord`, `DhikrPersonalRecord`, `KnownVersionRecord` (kept apart so a pending delete keeps its version), `OutboxCommandRecord` (ordered by `position`; a replaced command keeps it unless it moves after a later put it references), `SyncConflictRecord`, `SyncNoticeRecord`, `SyncPositionRecord` (`after`). `SwiftDataSyncState` implements `SyncLocalState` over one `ModelContext`; `ProfileDatabase` saves once per rule (an edit and its command, a batch's receipts, a page with its `next_after`) and rolls back on failure. Local checks before saving: document validity, 100 tags, 1,000 custom dhikrs, 20 tags per dhikr, a normalized name already taken. The registry's `after`, has data and has unsent are refreshed from the store after each change; the store is the source of truth.
  - **Audio:** MP3 or M4A only (the picker allows `UTType.mp3` and `.mpeg4Audio`; `ProfileFiles.importedType(of:)` checks the extension and the system's type, mapping `audio/x-m4a` to `audio/mp4`), so anything else, a raw `.aac` included, is refused at import with "unsupported type" (`audioUnsupported`). At most 10 MB (10,000,000 bytes), copied into the profile's staging area when picked, moved into place when the dhikr is saved; the document says `{"local_only": true}` until the recording is uploaded (slice 3c, below). Played with the same `DhikrAudioPlayer`.
- **Sync engine** (`AwradData/Sync/`):
  - `SyncPass`: marks up to 100 commands sent and saves before the request (a later edit then chains instead of replacing), sends them, applies the receipts (typed by each command's entity type), repeats until the queue drains, then reads `list_sync_changes` from `after` (200 per page) until `has_more` is false.
  - `SyncScheduler`: launch and foreground sync now, a local change after a 2 s debounce, every 5 minutes while active; a failure retries after `SyncBackoff` (5 s doubling to 5 min, ±20% jitter, at least `Retry-After`); one attempt at a time.
  - **Safety:** an attempt runs only when the registry's signed-in account owns the active profile *and* `AccountService.signedInAccount()` agrees; signed out there are no requests at all. Every request carries `X-Awrad-Account`; `409 account_mismatch` stops syncing that profile (`SyncStatus.accountMismatch`).
  - **Wire** (`SyncWireTypes.swift`): hand-written `SyncCommandBatchWire`, `SyncReceiptBatchWire` (each status encodes exactly its own members), `SyncChangesPageWire`; `APIOperation.postSyncCommands` and `.listSyncChanges` (bearer, `sendsAccountHeader`). `APISyncServer` sends them through `AuthSession.authorized`. A refresh answered `401 account_deleted` signs out like a revoked session and records the account (`takeDeletedAccount()`), and the profiles offer to remove its data.
- **UI:**
  - `FeatureLibrary`: the "Your dhikrs" tile, first in the Library's and Home's tile rows whenever the profile has custom dhikrs (the shell follows the library, so Home knows), and its list; the + on the Library header; the tag filter as `AwradFilterChip`s under the search field (AND); search over custom dhikrs; the "Change refused" dialog for each rejected change (already undone; the reason and OK). `CustomDhikrEditorRoute` (Arabic, kind, per-language title/transliteration/translation behind segmented pills, the Arabic, transliteration and translation in the multi-line field, references, tags, local recording through `.fileImporter`, save, delete with confirmation). The dhikr detail shows user tags and Manage tags for every dhikr, the Sources section (`Dhikr.sources`: the references not in the card or under a virtue, so all of a custom dhikr's), Edit and Delete for custom ones, and the conflict banner with Keep mine / Use theirs. `ManageTagsRoute` creates, renames and deletes tags (a tag's conflict banner names it), and toggles them on a dhikr.
  - `FeatureAccount`: the sign-in question (Add to my account / Erase), sign-out and ended sessions reported to `LocalProfiles`, a Sync card and "Profiles on this device" (Remove from this device, with the unsent-changes warning; "Account deleted" on a kept profile of a deleted account). `awradProfilePrompts(_:)` shows the account-deleted question (Remove / Keep); `RootView` applies it to the root and the account sheet.
  - **Screenshots** (debug builds): `-AwradSampleData YES` seeds an empty active profile (two custom dhikrs, three tags, a conflict); `-AwradLibraryYourDhikrs YES`, `-AwradLibraryEditor new|<id>`, `-AwradLibraryManageTags all|<dhikr id>`, `-AwradLibraryFilter <tag id>`, `-AwradLibraryDhikr <custom id>`; `-AwradAccountScreenshot profiles|signInPrompt|settings`.
- **Tests:** `SyncEngineTests` (a `FakeSyncServer` with the README's rules: applied with `cascaded`, duplicate after a lost response, conflict with Keep mine and Use theirs, merged tags rewritten in one batch, gone, rejected with a notice, paging, account mismatch, retry), `ProfileSwitchingTests` (anonymous edits unqueued and no requests, add/erase, merging into an existing profile, sign-out queueing, a second account's own profile, removal, relaunch, account deleted removed or kept, updates following a switch), `SyncTransportTests` (headers, query, `409`, `account_deleted`, the real stack signed out makes no request, backoff, debounce), `SyncPersistenceTests`, and the feature model tests.

## Private audio (slice 3c)

A signed-in user's custom dhikr recording follows the account ([`contracts/audio/v1`](../contracts/audio/v1/README.md), root ADR-2026-10-29). Signed out nothing changes from 3b: recordings stay `{"local_only": true}` and the app makes no audio request.

- **Domain** (`AwradDomain/Audio/`, pure and fixture-driven):
  - `CustomDhikrAudio` is the document's `audio`: `.localOnly` or `.uploaded(UploadedAudio)` (`asset_id`, `byte_size`, `content_type` as `AudioContentType`, `duration_ms` or `null`), `nil` for none. `CustomDhikrDocument.audio` replaces 3b's `hasLocalAudio`; `CustomDhikrValidation` accepts exactly the three shapes (anything else is `invalid` on `/audio`).
  - `AudioUploadRules.check(byteSize:contentType:usedBytes:limitBytes:)`: type (exact string), then size (1–10,000,000), then quota (`used + size ≤ 500,000,000`), returning the first `AudioUploadError`. `AudioContentType(fileExtension:)` maps `.mp3`/`.m4a`; `AudioContentType(importedMediaType:)` maps `audio/mpeg`, `audio/mp4` and `audio/x-m4a`. `AudioUsage.megabytes` writes whole decimal megabytes, rounded down, in the locale's digits.
  - **Audio rejections** (`SyncRules+Audio.swift`): `SyncRules.apply(_:to:localAudioFiles:newCommandID:)` returns a `ReceiptsOutcome` (notices and `uploadsQueued`). A custom dhikr put rejected `audio_not_found` or `audio_mismatch` keeps the local document, sets `audio` to `.localOnly` when its file is on the phone (and queues the upload again) or `nil`, takes the server's version, and replaces the entity's unsent commands with one put inserted where the rejected put was (`SyncLocalState.insertCommand(_:at:)`); a locally deleted dhikr gets a delete on the server's version instead, or nothing. The notice keeps its code.
  - Ports: `PersonalLibrary` gains `downloadAudio(for:)` (`AudioDownloadError`), `dismissAudioNotice(_:)` and `PersonalContent.audioNotices` (`AudioUploadNotice`: the dhikr, an `AudioUploadFailure`, and the usage for `storage_full`); `ProfilesState.audioUsage` carries Settings' storage.
- **Runner:** `AudioFixtures` runs `audio_upload_validity.json`; `AudioFixtureTests` checks the directory is covered. `SyncFixtures` reads `local_audio_files`, `new_command_ids` and `uploads_queued`, and `SyncFixtureTests`/`SyncPersistenceTests` run every `apply_changes` case in memory and on SwiftData through the same `ApplyChangesGiven.run(on:)`.
- **Wire** (`AwradData/Network/AudioWireTypes.swift`): hand-written `AudioUploadRequestWire`, `AudioUploadWire` (`upload_headers` as an opaque map), `AudioAssetWire`/`AudioAssetResultWire`, `AudioCreateResponseWire` (the pending link or `{asset}`, told apart by `asset`), `AudioDownloadWire`, `AudioUsageWire`; `ProblemWire` keeps `used_bytes`/`limit_bytes`. `APIOperation.createAudioUpload`, `.completeAudioUpload`, `.getAudioDownload`, `.getAudioUsage` (bearer, `X-Awrad-Account`; the POSTs carry an `Idempotency-Key` the server ignores). `OpenAPIContractTests` checks them and round-trips every example.
- **Seams** (`AwradData/Audio/`, ADR 0004): `AudioServer` (the four operations; `APIAudioServer` over `AuthSession.authorized`, with the codes the engine handles returned as an `AudioRefusal` value so the session only sees shared failures) and `ObjectStore` (`URLSessionObjectStore`: its own ephemeral session, `upload(for:fromFile:)` with exactly `upload_headers`, `download(for:)`; never the bearer token). `AudioServices` bundles them for `LocalProfileStore`. Doubles: `FakeAudioServer` and `FakeObjectStore` in `AwradDataTests`.
- **Upload queue** (`AudioUploadRecord` in the profile's store, beside the outbox; `PendingUpload`): one entry per dhikr with a UUIDv7 `asset_id`, the file name, its SHA-256 (CryptoKit, `AudioFileFacts`), `byte_size`, `content_type`, `duration_ms` (AVFoundation, `nil` if unreadable), a stage (`reserve`, `complete`, `attach`, `failed`), whether the server holds the reservation, and mismatch retries. Entries survive restarts. Replacing or removing a recording, or deleting the dhikr, drops its entry.
- **Upload engine** (`AudioUploadEngine`), run by the sync attempt before the queue is sent (so only signed in as the profile's account, and the put leaves in the same pass):
  1. every `.localOnly` dhikr with an imported file and no entry gets one (an import, "Add to my account", a merge, a re-queued rejection, a crash);
  2. the rules are checked on the phone first, with `get_audio_usage` read once per run, for entries not yet reserved;
  3. reserve, `PUT` the file, confirm; `200 {asset}` on reserving skips to the end;
  4. hard-link the file into `Audio/Cache/<asset>.<ext>`, then in one transaction set the document's `audio` to the asset (size and type copied from it), queue the put (`SyncRules.save`, replacing an unsent local-only put in place) and drop the entry.

  | Answer | Effect |
  |---|---|
  | `413`, `415`, `invalid_size`, `storage_full` (server or pre-check) | Entry kept as `failed` (not retried until the recording changes), `AudioUploadNotice`; the dhikr syncs as local-only |
  | `storage_full`, on a later sync | Queued again (and its notice dropped) once `get_audio_usage` shows room for its `byte_size`; replacing or removing the recording also clears it |
  | `upload_incomplete`, `404` on completing, storage refusing the `PUT` | Reserve again (same asset, fresh link), `PUT`, confirm |
  | `upload_mismatch` | Once: start over under a new asset with the file re-hashed; a second time: failed with `upload_mismatch` |
  | `asset_id_in_use` | Start over under a new asset |
  | No connection to storage, or 8 steps without finishing | Entry kept; the attempt reports a failure so `SyncScheduler` backs off and retries |
  | API failures (`401`, `409 account_mismatch`, `429`, offline) | As the change queue's (`SyncFailure`) |

  `LocalProfileStore.syncWithAudio` runs uploads, then `SyncPass`; if receipts re-queued recordings, it puts each file back as the imported file (a link from the cache) and runs both once more. Then it reads the usage for Settings and sweeps.
- **Files and the cache** (`ProfileFiles+Audio.swift`): `Audio/<dhikr>.<ext>` is a recording imported here and not yet uploaded; `Audio/Cache/<asset>.<ext>` an uploaded one; downloads land in `Cache/Partial/` and are renamed into place (atomic), replacing a copy already there with `replaceItemAt`; a download that can't be stored leaves nothing in `Partial/`. `sweepAudio` (after each sync and each recording or dhikr change) deletes cached copies no document names (a replaced, removed or deleted recording, here or elsewhere) and imported files whose dhikr is no longer local-only, unless an upload is under way. `recordingFiles` (imported, else the cached copy of the document's asset) is `local_audio_files` for the rejection rule.
- **Playing:** `audioURL(for:)` is the imported file or the cached copy, never the network. `downloadAudio(for:)` returns the cached copy, or (signed in as the profile's account) asks `get_audio_download` for a link, downloads, and stores it; later plays work offline. `DhikrDetailModel` and the editor show the player for an uploaded recording that isn't here (the editor's `Recording.inAccount`); the first play sends `.playPauseTapped` to `send`, which downloads and plays through the same `AVDhikrAudioPlayer`, or shows the player's failure.
- **UI:** the Library shows one notice dialog at a time (`PersonalNotice`): refused changes first ("Recording not in your account" for the audio codes: the change was kept), then "Audio couldn't be uploaded" with the reason ("storage is full (497 MB of 500 MB)"). The account Sync card adds "Audio storage: 120 MB of 500 MB" while `ProfilesState.audioUsage` is set (signed in as the active profile's account).
- **Screenshots** (debug builds): `-AwradSampleData YES` now includes a dhikr whose recording is in the account (`LocalProfileStore.Sample.tasbih`); `-AwradSampleAudioNotice YES` adds a storage-full notice; `-AwradAccountScreenshot settings` shows the storage line.
- **Tests:** `AudioUploadTests` (success with exact headers and the resulting put, the phone's pre-check, each refusal, incomplete, one and two mismatches, `storage_full` retried once there's room, a removed failed recording, ID in use, unreachable storage, restart, signed out, "Add to my account", an `audio_not_found` round trip, a replaced recording), `AudioCacheTests` (first play, offline replay, a changed, removed or deleted recording, signed out, not found, Settings' usage), `AudioImportTests` (accepted and refused types, a raw `.aac`, an `.m4a` sent as `audio/mp4`), `UploadedAudioTests` (including the document's length before the first play) and `AudioStorageTests` for the screens.

- **Strings:** String Catalogs per module (`Bundle.module`) plus the app's own. ## Components

`AwradDesignSystem/Components` implements [`contracts/design-system/v1/components.md`](../contracts/design-system/v1/components.md) with tokens only. Every component draws disabled at `AwradState.disabledOpacity` (`.disabled(_:)`), presses with `press`, mirrors in right-to-left, scales its text with Dynamic Type (heights are minimums), and turns movement into the cross-fade with Reduce Motion.

| Component | API |
|---|---|

| Content sheet | `AwradContentSheet { … }` (`surface`, `contentSheet` top corners, scrolls) with `AwradSectionTitle(_:)` |

| Option row | `AwradOptionRow(_:avatar:isSelected:selection: .single/.multiple, action:)`, the `check` icon (`iconSmall`) in an `onPrimary` circle when selected; read as selected, and as a toggle for `.multiple` |
