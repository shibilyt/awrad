# Decision: Dual Authentication Strategy

## Status

Accepted

## Date

2026-04-07

## Context

Awrad API serves two clients:

1. **Phoenix LiveView web app** — server-rendered, uses WebSockets, standard browser session model
2. **Android mobile app** — REST API consumer, needs offline-capable auth, no cookies

These clients have fundamentally different auth requirements. The web app benefits from session-based auth (CSRF protection, server-side session management, Phoenix's built-in session infrastructure). The mobile app needs stateless request authentication and long-lived credentials that survive app restarts.

## Decision

We use two independent authentication mechanisms from a single `User` schema:

1. **Web**: Phoenix session + signed cookie (generated by `phx.gen.auth`)
2. **Mobile API**: JWT access tokens (stateless, 15 min) + rotating DB-backed refresh tokens (180 days)

Both mechanisms share the `users` and `users_tokens` tables. The `context` field in `users_tokens` differentiates token types (`"session"`, `"refresh"`, `"login"`, `"change:*"`).

## Alternatives Considered

### JWT for everything

Rejected. JWTs are awkward for server-rendered web apps (no built-in CSRF, manual cookie management, can't easily revoke). Phoenix's session system is battle-tested and generated by `phx.gen.auth`.

### Session cookies for mobile

Rejected. Cookie-based auth requires cookie jar management on mobile, breaks with app restarts, doesn't support offline token storage well, and doesn't allow fine-grained token expiry control.

### Guardian for both

Rejected. Adds complexity for the web side where Phoenix sessions work perfectly. Joken is lighter-weight for just the JWT signing we need.

## Consequences

### Benefits

- Each client gets the auth mechanism best suited to its platform
- Web auth is standard Phoenix — all `phx.gen.auth` features work out of the box
- API auth is stateless per-request (no DB hit for access token verification)
- Shared user schema means one registration, one password, both platforms

### Tradeoffs

- Two auth code paths to maintain (session plugs + JWT plug)
- Token revocation for API requires a refresh token endpoint (access tokens can't be revoked until they expire)
- Must keep JWT signing secret secure in production
